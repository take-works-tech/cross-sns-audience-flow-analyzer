# Verification plan

Acceptance criteria say *what* must be observed. This says **how**: with what data, to what tolerance,
on what equipment. A criterion with no entry here is not verifiable, whatever it claims.

Feature-scoped AC numbering repeats across features, so every row uses the qualified id
(`sns-connection/AC-001`). No code exists yet: automated rows carry the method suffix `(planned)` and
name the intended test path; removing the word `planned` is the moment a row starts claiming coverage,
and from then on the named test must exist (check 14). Manual rows state a written procedure in the
pass condition.

Manual rows stay manual because their criteria are about what a person sees or holds: frame rate and
edge tracking on real hardware (canvas/AC-003, canvas/AC-007), particle-mapping legibility
(flow-animation/AC-001), tablet touch behavior (canvas/AC-013), notification delivery
(flow-analysis/AC-012), report content and failure (projects/AC-009, projects/AC-010), and EC sandbox
behavior (sns-connection/AC-009, sns-connection/AC-010). Recording those honestly beats an automated
check that passes while the screen is frozen.

Data provenance is not paperwork. A tolerance measured against a sample of unknown origin proves
nothing; every fixture above names where it came from so that a failing row can be reproduced.
